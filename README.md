## Problem
Many people struggle with recycling and are unsure how to correctly sort waste items, especially ones that don't clearly fall into a single category (a greasy pizza box, a mixed-material package, a broken electronic item). Waste categorization is governed by national legislation, but generic AI advice often gets the specifics wrong, creating real friction and real environmental cost when items are sorted incorrectly.

### Intended users
Residents and passers-by who want a quick way to check how to dispose of an item, wherever they happen to be.

### Problem statement
The application solves the problem of not knowing how to correctly categorize and dispose of a waste item, and additionally shows what the material actually becomes after recycling. This turns a moment of uncertainty into both a correct disposal action and a concrete understanding of where the material ends up. For items that cannot be recycled at home, it also shows where to take them: the nearest drop-off point or collection point.

### Why AI is appropriate
Identifying an item from a photo or a short, informal description, rather than a fixed dropdown list, requires flexible, natural-language and visual understanding that rigid, rule-based software cannot provide. A traditional deterministic lookup would require the user to already know the exact category name to search for, which defeats the purpose. AI is well suited to interpreting varied, informal input this way. The specific disposal rule returned is still grounded in real national regulatory content rather than the model's own unverified claims.

## Solution

WasteBuddy lets a user either photograph an item or type a short description of it, then returns two things: the correct disposal category and what that material is actually recycled into. If the input clearly isn't a waste item at all, for example an unrelated question, WasteBuddy says so plainly and invites the user to describe an item instead, rather than forcing a nonsensical classification. Disposal facts are always grounded in Finland's national waste regulations, never freely generated by the model. When the item cannot be recycled at home, such as hazardous waste, electronics, worn-out textiles, construction waste or garden waste, a "Where to take it" section appears right below the answer and finds the nearest drop-off point from the user's location or municipality. WasteBuddy also remembers the last few items a user has checked, shown in a collapsible "History" section, so a returning user doesn't lose track of what they've already looked up. This directly addresses the problem statement above by removing the guesswork from sorting.

## Main user workflow

1. **User Input:** The user submits a photo or typed text via the Gradio interface.
2. **Item identification:** If an image was provided, the application service layer calls a vision model (`moondream`) to produce a short item and material description. If only text was provided, the typed description is used directly.
3. **Classification (model-generated):** The service layer (`src/services/ai_service.py`) sends the item description to the text model (`qwen3:8b`), restricted to picking a single category id from a fixed list, or flagging that the input isn't a waste item at all. This is the only part of the answer the model generates itself.
4. **Grounding (dataset-generated):** If a real category was picked, it is looked up in [`data/finland_waste_categories.json`](data/finland_waste_categories.json), a curated reference table sourced from InfoFinland, Rinki, HSY, and LSJH. The disposal category name and the `recycled_into` fact both come from this lookup, not from the model. If the model instead flagged the input as off-topic, WasteBuddy replies with a short, friendly redirect back to waste sorting rather than a forced classification.
5. **Response:** A structured `RecyclingResponse` (see [`docs/architecture.md`](docs/architecture.md)), or the redirect message, is returned through the service layer to the UI, where it is shown in the **Answer** section.
6. **Memory:** Once a real classification is returned (never a redirect or an error), it's appended to a small local history file, so the **History** section can show a returning user their last few lookups without needing to repeat them.
7. **Drop-off point:** The category of the checked item is passed on, so the user is never asked again what they want to drop off. If the category has a drop-off option, a "Where to take it" section opens under the answer with a short, positive message for that category. The user presses "Use my location" (or enters a municipality or postal code) and `src/services/drop_off.py` asks the Kierrätys.info open API for collection points that accept that category, nearest first, with opening hours, what each point accepts and a directions link. Biowaste and mixed waste go in the household bins, so they get no drop-off section. Packaging materials (glass, metal, paper, cardboard, plastic) get the message "if your home or building has no collection for it, take it to a public collection point". The location is only used to build the API request: it is never stored, saved in the history or sent to a language model.
8. **Stop search:** While a search runs, a "Stop search" button appears. It makes the page stop waiting immediately, discards the answer and saves nothing to History (see Known limitations for what this does and does not stop).

## Architecture

Below is the current architecture. The detailed description of the architecture is in [`docs/architecture.md`](docs/architecture.md).

```text
User (photo or text)
  ↓
Gradio UI (app/ui.py, plus the optional app/drop_off_ui.py)
  ↓
Service layer (src/services/)
  ├─ ai_service.py       classification and grounded answer
  ├─ search_control.py   Stop search, and remembers the category of the checked item
  ├─ history.py          local log of past lookups
  └─ drop_off.py         nearest drop-off point lookup
  ↓
Model Client (src/models/model_client.py), called only by ai_service.py
  ├─ moondream  (vision model, used only on the photo path, to name the item and nothing else)
  └─ qwen3:8b   (text model, picks ONE category label from a fixed list, or flags off_topic)
  ↓
Ollama (Local LLM Server)

  + data/finland_waste_categories.json (deterministic lookup for every disposal fact)
  + data/user_history.json (local log of the user's own past lookups, service-layer only)
  + Kierrätys.info open API (collection points; called only by drop_off.py, never by the model)
```

> **Core Architectural Rule:** The user interface must NEVER communicate directly with the model client, Ollama, or the underlying data files. All interactions must pass through the service layer (`ai_service.py`, `history.py`, `search_control.py` and `drop_off.py`).

## Model

- **Text model:** `qwen3:8b`. Confirmed as the primary model after evaluation (see Evaluation below). Responses are slow on this hardware (multiple minutes per query), which the UI addresses directly (see Accessibility & UX).
- **Vision model:** `moondream`. Chosen for its small size (about 1.6B parameters) to leave VRAM headroom for the text model. Used only to name the item in a photo; it does not perform classification itself (see `docs/architecture.md` for why).
- **Selection rationale:** Initial testing showed `qwen3:8b` was slow for open-ended questions, but subsequent testing confirmed it produces reliable, correctly grounded classifications for this narrower, constrained task of picking one category id from a fixed list. That is a much easier job than open-ended generation. No fallback model was needed in practice.

## Accessibility & UX

- All Gradio input components use explicit `label=` values, which are exposed as proper accessible labels to screen readers, and every component, including the Tabs used to separate the text and photo paths, is natively keyboard-operable. This is a deliberate benefit of using Gradio's built-in component library rather than custom HTML controls.
- Submitting a query (text or photo) immediately shows a visible "Checking..." status message before the slow model response arrives, so the interface never appears frozen during the multi-minute wait `qwen3:8b` can take.
- The page is divided into clearly separated sections: **Check an item** (the two input methods as tabs, "Describe it" and "Upload a photo") next to the **Answer**, then the **Where to take it** drop-off section, which only appears after an answer that has a drop-off option, and finally **History**, collapsed by default and opened with its arrow, so it never gets between the answer and the drop-off information.
- While a search is running, a **Stop search** button appears in the Answer section, and the input fields are locked so a second search cannot start on top of the first. Pressing Stop returns the page to normal straight away.
- A dedicated Clear button lets users reset the text input without needing to select and delete it manually.

### Capability justification
Users often find it easier to photograph an item than to describe or categorize it themselves, especially for ambiguous items like mixed-material packaging or damaged electronics. Accepting both an image and typed text meets users wherever is most convenient for them, without forcing a single input mode. The image path uses a small vision model to produce a short label, which is then handled by the same downstream classification logic as typed text, keeping the two input paths consistent and equally reliable.

Memory is useful here too: a user often checks several items in one sitting, or comes back later wondering what they already looked up. WasteBuddy keeps a small local log of the last 50 checked items and shows the five most recent in the interface, so a returning user gets a lightweight personal sorting log without needing to re-describe anything. This is stored in a single local JSON file, `data/user_history.json`, read and written only by the service layer (`src/services/history.py`), matching the same architectural rule already used for the waste-category reference data.

External API integration is useful because some items cannot be recycled at home, and knowing the category is only half of the help: the user also needs to know where to take them. After an item is checked, WasteBuddy uses the open Kierrätys.info API (maintained by Suomen Kiertovoima ry, KIVO) to find collection points that accept that item's category, using the browser's location (only when the user presses the button) or a municipality or postal code. The facts about the item itself still come from the reference data, not from the API or the model, and the location is never sent to the model. The feature is self-contained in three files (`src/services/drop_off.py`, `app/drop_off_ui.py` and `tests/test_drop_off.py`) and can be removed by deleting them, because the interface only imports it optionally.

## Setup

### 1. Create the Conda environment

```bash
conda env create -f environment.yml
```

### 2. Activate the environment

```bash
conda activate wastebuddy-env
```

`wastebuddy-env` is a local name for the isolated set of packages this project needs (Gradio, the Ollama client, Pydantic, and so on), kept separate from whatever else is installed on your machine. It is not shared over a network or between people: each team member creates and activates their own private copy of it by running step 1 on their own computer.

This environment was deliberately given its own dedicated name rather than reusing the course starter template's generic `dev-ai-project` name. Conda environment names are unique per machine, not per project folder, so if you have also completed another AI Application exercise locally that still uses the generic name, this keeps WasteBuddy's dependencies fully isolated from it, a change to one project's packages can no longer accidentally affect the other.

### 3. Configure environment variables

Copy `.env.example` to create your local `.env` configuration file:

On Linux / macOS:
```bash
cp .env.example .env
```

On Windows (Command Prompt / PowerShell):
```powershell
copy .env.example .env
```

Ensure `.env` contains valid values for `OLLAMA_BASE_URL`, `MODEL_NAME`, and `VISION_MODEL_NAME`:
```env
OLLAMA_BASE_URL=http://localhost:11434
MODEL_NAME=qwen3:8b
VISION_MODEL_NAME=moondream
```

The drop-off finder also needs a free Kierrätys.info API key. This is optional: without it everything else works, and only the drop-off lookup shows a message that the key is missing. Request your own key at https://api.kierratys.info/get_apikey/ (it is generated after you enter an email address) and add this line to your local `.env` file:

```env
KIERRATYS_INFO_API_KEY=your_api_key_here
```

Never put a real key in `.env.example` or commit it. `.env` is listed in `.gitignore`, `.env.example` is public.

No setup is needed for the memory feature: `data/user_history.json` starts as an empty list and is created automatically the first time a real item is checked.

### 4. Start Ollama

Make sure Ollama is installed and running locally, then pull the configured models:

```bash
ollama pull qwen3:8b
ollama pull moondream
```

### 5. Run the application

Run the application from the root directory of the project:

```bash
python -m app.main
```

Then open your browser at `http://localhost:7860`.

**To test from a mobile phone:** by default the app only listens on `localhost`, which a phone cannot reach. Launch with network access enabled (binding to `0.0.0.0`) and open your laptop's local network IP from a phone on the same Wi-Fi, or use Gradio's `share=True` option for a temporary public URL.

### 6. Run automated tests

```bash
pytest
```

The tests cover the service layer, the history, the drop-off finder and the Stop-search logic. They use a fake model and a fake API, so they need neither Ollama nor an API key.

## Evaluation

A 12-case evaluation dataset and script are in [`evaluation/`](evaluation/), covering three categories: typical and successful inputs, difficult and edge-case inputs, and failure and adversarial inputs such as empty input, whitespace, and out-of-scope questions. Run it with:

```bash
python -m evaluation.run_evaluation
```

Latest recorded run: 9 of 12 cases were automatically graded as correct, 0 failed, and 3 were flagged `partial` for manual review, since those cases have no single objectively correct answer. **This run predates the off-topic-handling and memory updates above.** Case-12 (the out-of-scope question) is now graded automatically against a required phrase in the redirect message rather than left as `partial`, and is expected to pass once re-run, since WasteBuddy no longer forces a classification onto out-of-scope input. Re-run the command above after pulling these changes and update the numbers here and in [`evaluation/evaluation_results.md`](evaluation/evaluation_results.md) rather than assuming the outcome; the graded raw output is in [`evaluation/test_cases.json`](evaluation/test_cases.json). The construction waste and garden waste categories and the drop-off finder were also added after that run, so the evaluation should be re-run once more before the final submission.

## Known limitations

- Scoped to one country's (Finland's) national waste categorization rules as a proof of concept, not generalized to other countries.
- National-level guidance identifies the correct disposal category but does not capture municipal-level operational details, such as bin color or collection schedule, which vary by local waste operator.
- Classification is single-label. The system cannot express nuance like "recycle the clean part, bin the dirty part" for a contaminated item, even when the reference dataset itself notes that distinction.
- The off-topic check is not a separate, independently verified filter: the same single model call that classifies an item is also asked to judge whether the input is a waste item at all, so unusual or borderline phrasing may occasionally be misrouted in either direction, rather than being guaranteed correct.
- **UI language:** the user interface (all texts, buttons and messages) and the answers are in English only. There is no language selection.
- Input in other languages is not officially supported. Some words given in Finnish or Swedish may be recognised by the underlying model, but this has not been tested or verified, so the result (the identified item and its category) cannot be relied on.
- No live or updating source for regulations. Rules are represented as static reference content at the time of writing.
- History is stored only in a local file on the machine running the app. It is not synced across devices and is not shared between users.
- Construction waste and garden waste rules depend on the local waste company (what is accepted, where, and the price), so those categories only give general guidance and tell the user to check their own waste company's instructions. Their sources come from individual waste companies (HSY, Salpakierto, LSJH), not from one national rule. Bulky waste such as furniture is not covered.
- The drop-off finder needs a free Kierrätys.info API key per installation (see Setup), and a missing key only affects this feature. It only covers Finland, and the data (opening hours, accepted materials) comes from Kierrätys.info and can be out of date, so users are told to check before they go.
- Drop-off matching works at category level, not item level. For example, the nearest hazardous waste point may not accept every kind of hazardous item, so each result lists what the point accepts. Searching by municipality returns the first results from the API, which are not sorted by distance. Only the location button sorts nearest first.
- The Stop search button makes the page stop waiting and discards the answer, but the local model may keep computing in the background until it finishes, because Ollama cannot be interrupted mid-reply with the current non-streaming call. A stopped search is never saved to History.
- The category of an item still comes from the language model, so a wrong classification leads to the wrong drop-off section.
- Response times of multiple minutes per query on this hardware are a real usability constraint, mitigated in the UI with immediate loading feedback but not eliminated.

## Future improvements

- **UI language selection:** let the user choose the language of the interface (for example English, Finnish and Swedish), with translated texts, category names and answers. Translations of the reference data should be checked by a person, because the disposal facts must stay accurate.
- **Language:** Full Finnish-language support, currently running only in English.
- **Worldwide expansion:** the architecture separates item identification from country-specific rule grounding, so supporting additional countries only requires adding a new grounded rule set per country, not re-architecting the app.
- Add confidence handling for ambiguous images, asking a clarifying question instead of guessing.
- Expand grounding into a proper RAG pipeline over full national regulatory documents, rather than a smaller curated reference set.
- **Landing page / general knowledge mode:** let the user choose between getting help with an item and browsing general information about waste and recycling (an idea we analysed but have not built).
- Show the Finnish category names next to the English ones, which the reference data already contains.
- Make Stop search stop the model as well, by streaming the model reply and closing the connection.
- Match drop-off points at item level (for example batteries and light bulbs, which the API lists separately from hazardous waste), and show a plain link to kierratys.info when no API key is configured.
- Add more categories where the rules allow, such as bulky waste.
- Move recent-item history from a flat JSON file to a lightweight local database (e.g. SQLite) if richer search or a longer history is wanted later.
